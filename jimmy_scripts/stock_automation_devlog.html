2026-10-08　排程觸發源換成本機 launchd：GitHub cron 降級為備援排程基礎設施

需求：10-02 那次（見下一則）只處理了「排程遲到造成的連坐失敗」，沒有處理遲到本身。 10/06 排程整次被丟掉——不是遲到，是整天沒跑，當天國泰漲跌／除息日曆／跌幅查詢頁／加碼損益全缺， 需人工補跑。到了必須換掉觸發源的時候。

實作：先用 GitHub API 把執行拆成「建立／排隊／實際執行」三段，證明排隊 0 分、執行 0.4~4.5 分， 遲到 5h08m~8h35m 全發生在 GitHub 決定建立執行之前，與工作量無關（非交易日只跑 0.7 分照樣遲到 7h47m）。 改由本機 launchd 每天 14:30 執行 trigger_wealth_sync.sh 打 API 觸發 workflow_dispatch（實測秒級啟動）；GitHub cron 保留當備援，Mac 沒開機那天退回原本的行為。 細節與踩坑見 Wealth OS 開發紀錄 同日條目。

踩坑與解法：

  • macOS TCC：launchd 讀不到 ~/Downloads。整個專案放在那底下， 所以觸發腳本不能 import twse_hist／source _load_pat.sh，必須完全自足並安裝到 ~/Library/Application Support/。這條對所有「本機排程跑專案腳本」的構想都成立， 日後要再加 launchd 工作（例如 YouTube 自動摘要）會同樣撞到。
  • 兩次把猜測當結論。①先改 cron 時段想避開擁塞，無效且疑似害 10/06 整次被丟； ②提議「讓腳本自動補漏跑的日子」，查了才發現 workflow_dispatch 只有 job 一個 input、 守衛固定用 today()，根本無法指定過去日期。 共同點都是在查證機制之前就先給方案。

驗證結果：四條分支與兩道保護（自判交易日、今天已成功不重複觸發）皆以真實資料實測通過； 漏跑偵測模擬 runlog 缺 10/06 時正確抓出。「交易日當天準時觸發」待 10/08 14:30 首次真實執行驗證。 預期效果：準時 14:35 完成（原本 20:00~23:10）；Mac 關機那天退回 GitHub cron，不會更差。

2026-10-02　排程遲到引發的連坐失敗：新增 --skip-if-exists排程基礎設施

需求：當天排程遲到 6.5 小時未觸發，手動補跑後排程才姍姍來遲， 結果整個 workflow 顯示 failure、LINE 推失敗通知，但資料其實是正確的。要讓這種情況不再誤報。

實作：update_stock_price.py 的 update 新增 --skip-if-exists： 當天快照分頁已存在時印訊息並正常結束（exit 0）而非 sys.exit 中止； wealth_sync.yml 的「更新股價」步驟帶上該參數。手動執行不帶參數時維持大聲中止的舊行為 ——那時候多半是真的想重跑，應該被明確告知，只是訊息裡補上提示有這個參數。

踩坑與解法：

  • 失敗的代價遠大於「一個紅燈」。原本以為只是誤報，查 job 步驟才發現 exit 1 讓 GitHub Actions 連坐跳過後面五個步驟。其中四個步驟 （國泰漲跌／ETF除息日曆／跌幅分布查詢頁／正二分析部署）各自抓自己的 TWSE 資料， 與那份快照毫無關係——被跳過等於那天這些資料整天空缺，而使用者只會看到一則 LINE 失敗通知， 不會知道跌幅頁沒更新。判斷一個失敗「無害」之前，要先看它連帶跳過了什麼。
  • 改錯了防呆。第一版改的是 new_title in props 那道，實測才發現當天實際觸發的是 更前面的 new_title == src_title（最新分頁本身就已是今天日期）。 兩道都要支援。這也說明光讀程式碼不夠——拿真實資料跑一次才知道走哪條路。

驗證結果：以真實試算表實測兩種情境：不帶參數 → 維持 exit 1 並提示有此參數； 帶 --skip-if-exists → 印 「[skip] 最新分頁已是當天日期「Jimmy_261002」…後續同步步驟照常進行」且 exit 0。 兩種情況都不會寫入任何資料（在建立副本前就返回）。

2026-09-30　記帳延遲的連鎖效應：成本口徑、缺漏還原與歷史回填Wealth OS記帳

需求：貼 9/24 禾伸堂賣出截圖時已隔 5 天，衍生出三個問題：①02_每日漲跌 的 「淨投入資金」把賣出算在補記日 9/29 而非成交日；②元大 App 顯示剩餘成本 894.76、試算表卻是 815.02； ③「股票買賣紀錄」分頁缺了 150 股的買進明細。

實作：三件事分頭處理——成本口徑：驗算發現 App 的賣出成本 155,030 ＋ 剩餘 89,476 ＝ 244,506，與試算表 815.02×300 差 0.00，證明是 FIFO 與加權平均的分攤差異而非算錯，Jimmy 選擇維持加權平均； 缺漏還原：用「快照差分法」掃 169 個 Jimmy_YYMMDD 分頁逐日比對均價與股數， 還原出完整買進批次；回填：直接改 16_資產歷史 該日列，再讓 --full 從它重建 02_每日漲跌。細節見 Wealth OS 開發紀錄 的 09-24／09-29／09-30 三筆。

踩坑與解法：

  • 記帳延遲是系統性問題，不是單次失誤。所有「成本相對前一日變化」的欄位都以持股表現況為準， 交易當天沒記，效果就會落在補記那天，還會與當天其他交易互相抵銷而變得看不出來 （本例四筆買進 +123,637 與賣出 −163,004 抵銷成 −39,367）。根治方法是當天記； 已補記的只能走回填流程，而 update_wealth_os.py 沒有指定來源分頁的參數， --date 舊日期 只會把最新持股貼上舊標籤，不能用來回填。
  • 三個互相矛盾的成本數字其實自洽。815.02（試算表均價）、775.15（App 賣出成本）、 894.76（App 剩餘成本）看似打架，突破口是先驗算總額——兩邊都是 244,506。 同樣手法也用來判斷誰對誰錯：快照與券商 App 兩個獨立來源都指向 244,506， 因此「股票買賣紀錄」6 月那兩筆短記 9,444，已留痕待查 6 月對帳單。
  • 手動參數不會隨交易連動。現金在 12_設定 B6，賣股實收的 161,376 不會自己進帳， 淨資產會一直短少；而 16_資產歷史 的淨資產是寫死的當日快照值，改參數只更新重跑當日那一列， 歷史列要自己補算。

驗證結果：淨投入資金 9/24 由 0 → −163,004、9/29 由 −39,367 → +123,637； 16_資產歷史 僅改目標列、其餘 62 列逐格零差異；還原出的四個買進批次合計 244,506， 且各批「成本 − 價金」皆符合手續費 0.1425%×6折（67／37／39 vs 理論 67.2／37.4／39.0）； Dashboard 淨資產與歷史列吻合。未補假交易湊平缺口，9,444 差額留待對帳單查明。
